# SkillTree — план до 30 октября 2026 года

## Основание и рабочий объём

19 октября пользователь указал срок до 30 октября и желаемую готовность около 50%. Модули разрабатываются последовательно. Публикация в Sites исключена.

Для планирования первая функциональная часть — пункты 0–10. Это интерпретация цели «50%» по завершённому пользовательскому сценарию, а не процент написанного кода и не равное распределение трудоёмкости между модулями.

Сценарий сдачи: человек открывает карту навыков → выбирает профессию → видит необходимые технологии и близкие роли → сохраняет траекторию → корректирует её → входит в аккаунт → ведёт личные записи и прогресс → публикует выбранную версию → получает комментарий и реакцию другого пользователя → управляет видимостью профиля.

## Ранние решения и критерии

- Рабочий стек: React + TypeScript + Vite; Node.js + NestJS; PostgreSQL + Prisma; REST + OpenAPI.
- React Flow — первый кандидат. При неудовлетворительном прототипе проверить причину и сравнить Sigma.js, не поддерживать два движка без необходимости.
- Ожидаемый каталог — менее 1 000 вершин. Основные наборы ранней проверки: 100, 300, 800 с реалистичными связями и подписями. 1 000 — возможная проверка запаса.
- 19 октября проведены замеры настоящего React Flow в Edge на production-сборке: [результаты](GRAPH_VALIDATION.md). Предыдущие интерактивные иллюстрации не использовались как доказательство производительности.
- Один сервер с модулями, одна БД. Внешние очереди, отдельный Python-сервис и дополнительные базы подключаем только при появлении задачи, которая этого требует.
- До аккаунтов сохранение ранних модулей может использовать локальный адаптер. При подключении сервера предусмотреть явный перенос локального черновика владельцу; локальное хранение не объявлять защищённым аккаунтом.

## Что нужно проверить перед сдачей

1. Маршрут включает несколько обязательных предпосылок; группа альтернатив не превращается в требование изучить все варианты.
2. Переключение вкладки группы не теряет вершины, связи, выделение маршрута и выбранную карточку.
3. Сохранённый малый граф открывается с теми же вершинами и связями; редактирование не меняет общий каталог.
4. Пользователь А не получает личные данные пользователя Б ни по странице, ни по API, ни через идентификаторы вложенных объектов.
5. Публикация содержит только выбранные данные; новые личные записи не появляются в уже опубликованной версии.
6. Приватный профиль не раскрывается через список графов, комментарии или прямые запросы. В публикации показывается только выбранное публичное имя автора; расширенный профиль может оставаться закрытым.
7. Данные переживают перезапуск сервера. Есть миграции и инструкция локального запуска.

- Архитектура и схема главного экрана: подготовлены, рабочий прототип использует карточку справа и переносит её вниз на узком экране.
