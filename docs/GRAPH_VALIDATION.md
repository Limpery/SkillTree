# Проверка графа SkillTree — 19 октября 2026

Исторический эксперимент до перехода на последовательные траектории, впоследствии заменённые графом Middle React с параллельными ветвями. Таблицы и исходный JSON ниже относятся к прежней раскладке с 8 профессиями. Эти цифры не описывают текущую версию. Проверка новой раскладки: [отчёт](LAYOUT_VALIDATION.md).

## Решение

Оставить React Flow рабочим движком для следующего этапа, используя смысловые группы, раскрытие вблизи видимой области и отрисовку только видимых элементов. В проверенном обычном режиме набор из 800 исходных вершин укладывается в предварительные ориентиры: примерно 109 мс на выбор профессии и отображение карточки, около 97 кадров/с по интервалам requestAnimationFrame.

Показ всех 800 вершин одновременно остаётся диагностическим режимом: выбор и обновление карточки заняли около 258 мс, что выше предварительного ориентира 150 мс. Это ограничение сохраняется в отчёте. Замена библиотеки по результатам обычного сценария сейчас не требуется; при изменении состава/сложности вершин или требований проверка повторяется.

Эти результаты относятся к указанному компьютеру и техническому прототипу. Они не подтверждают производительность будущих курсов, редактора, запросов к серверу или других устройств. Пункт 0 целиком ещё не закрыт: пример сохранения в PostgreSQL остаётся впереди.

## Реализация эксперимента

- Настоящие React 19.3.1 и React Flow 12.12.0, TypeScript 7.0.2, Vite 8.3.4; версии зафиксированы в манифестах и lock-файле.
- Общая модель графа отделена от React Flow: один ID на технологию, группы меняют только представление, обязательные зависимости и альтернативы учитываются отдельно.
- Центральная база, направления во все стороны и 8 профессий на периферии.
- Поиск в подготовленном каталоге, выбор специальности и показ её требований — технические сценарии, а не законченный модуль 2.
- Общая технология встречается в нескольких профессиях без создания её копий. Просмотр общей темы внутри траектории сохраняет выбранную профессию.
- На увеличении раскрываются близкие к видимой области группы; при отдалении они сворачиваются с разными порогами. Принудительно выбранная технология остаётся доступной.
- Устойчивые ссылки на параметры React Flow и ограничение частоты обновления подписи масштаба устраняют лишние обновления при движении камеры.

## Методика

Windows 11 (10.0.26200), Intel Core i5-12450H, 12 логических процессоров, 16 ГиБ RAM. Node.js 25.0.0. Microsoft Edge 155.0.4283.62, headless, viewport 1440×1000, device scale factor 1. Production-сборка. По 3 новых браузерных контекста на каждую комбинацию размера и режима.

Наборы воспроизводимы и содержат ровно 100, 300 или 800 вершин, включая специальности. Дополнительные темы синтетические, с реальными связями и группами; они не выдаются за проверенную образовательную программу.

Три режима:

1. **Обзор** — 14 свёрнутых групп и 8 специальностей, всего 22 отображаемые вершины.
2. **Локальное раскрытие** — обычный режим после приближения к центру до масштаба 1.1. Группы за пределами области остаются свёрнутыми; часть переданных движку вершин находится вне экрана и не создаёт DOM-элементы.
3. **Все вершины** — диагностический показ всех тем и зависимостей, с масштабом, помещающим их на экран.

«Готовность» измеряется внутри App до подготовки и размещения вершин; загрузка файлов, запуск браузера и сеть в эту величину не входят. Для локального раскрытия в таблице указана исходная готовность обзора, а движения и выбор измеряются уже после приближения. Это не время полной загрузки страницы.

Движение/зум задаются на 100 последовательных requestAnimationFrame; первые 5 интервалов исключены. FPS — обратное среднему интервалу, то есть приближённая оценка ритма работы браузера, а не измерение реально показанных монитором GPU-кадров. Выбор выполняется DOM-нажатием одной и той же кнопки профессии в боковой панели и заканчивается после обновления карточки и двух следующих кадров. Он не включает задержку физического устройства ввода.

В таблице — медианы трёх повторов; исходные интервалы p95 и отдельные повторы доступны в JSON. Фоновая нагрузка ОС и частота обновления влияют на повторяемость. Память в JSON — только JS heap, не вся память процесса, DOM или GPU.

## Проверка корректности

11 проверок модели (`npm test`): один ID общей технологии, несколько профессий, все обязательные предпосылки, выбор одной СУБД из альтернатив, неизменность каталога при группировке, сохранение общих требований, контекстные связи, циклы в том числе вне готовых маршрутов, отсутствующие ссылки и наборы 100/300/800.

6 браузерных сценариев (`npm run test:browser`): раскрытие группы и карточка JavaScript, поиск Java без ошибочного выбора JavaScript backend, общий Git и одна выбранная СУБД в пути, настоящий набор 800, узкий экран без горизонтального переполнения, раскрытие близких групп при зуме и сохранение цели при просмотре общего навыка. Ошибок страницы в итоговом benchmark нет.

Проверка типов и production-сборка (`npm run build`) проходят. Получившаяся сборка: примерно 436 КБ JS (138 КБ gzip) и 35 КБ CSS (8 КБ gzip).

## Повторение

```powershell
cd C:\Projects\SkillTree
npm ci
npm test
npm run build
npm run test:browser
npm run benchmark
```

Нужен установленный Microsoft Edge; CLI-тесты запускают отдельный профиль headless и не используют личные вкладки. Скрипт benchmark поднимает production preview на 127.0.0.1:5177, сохраняет JSON и снимки, затем закрывает его и браузер. Обновление отчёта Markdown после нового прогона выполняется отдельно по итоговому JSON.

## Остающиеся вопросы

- Проверка PostgreSQL и правил хранения общего каталога, личного графа и записей.
- Экспертный состав настоящих траекторий и уровни компетенций; демонстрационные роли не являются обещанием работы.
- Проверка читаемости на пользовательских устройствах и подготовленном реальном каталоге.
- Детали смены масштаба и ручного раскрытия, ограничения изменения координат в основном просмотрщике.
- Полный режим 800: задержка выбора выше ориентира; дальнейшая оптимизация потребуется, если такой режим станет основным требованием.
